Carbon Paper/Claims review mock/plan

Attacking a claim

The skill that reads a submitted claim, one cell of one run's output, against the run it cites and produces the page at What this run says. Written against 🟣 #973 (the claim service) and 🟣 #927 (the submit screen), which this sits after. Scratch document; nothing here is committed.

One paragraph

A claim is a sentence a person proposes to publish, citing one cell of one run's output (StageOutputCellCitation). A claim that cites a table is out of scope here. Attacking it means reading the sentence against everything that run holds and returning, per load-bearing phrase, what it rests on and every way it could be wrong, each weighed. The result is stored once per claim, shown on one page, and closed by one button: Approve, which is approve_claim from #973. Nothing in the attack reruns the workflow.

Dispatch is code, not a model: start_claim_attack gathers the evidence once, runs the six attackers as app.core.agent.Agent turns with their own target_schema, then runs one orchestrator turn over their answers. The engine passes no agents= to the SDK today, so "subagent" here means an Agent with its own prompt, tools and schema, the way app/compiler/review_guide.py already builds one. Parallelism is asyncio.gather over six coroutines on the server loop, the same loop generation.py requires.

Attackers never see each other. The orchestrator is told it will be shown beside the sentence to a person deciding whether to approve, that nothing it writes changes the claim, and that a challenge it cannot back with a number goes in at severity 1 or below.

Severity, and the fold

Weight 0 is folded with a count. The rule that keeps the list short is the same one on the mock: a challenge that does not move the figure at the precision it was printed at is not open.

Records

One new record, declared in app/models/records/claim_review.py, PROJECT_READ, immutable. A re-attack is a new claim and a new review; the old pair stays as the audit trail.

ClaimReview                          one per claim, written once, nothing on it moves
  claim_id, run_id
  grounding: list[Grounding]         span start, end · evidence: EvidenceRef | None
  challenges: list[Challenge]        attacker, kind, grounding_index, text, evidence,
                                     backing, severity, moves, cost, raised_by
  proposed_rewrites: list[Rewrite]   text, why · taking one is submit_claim with new text
  summary: str                       the orchestrator's two or three sentences, read first
  session_ids: list[ID]              the seven transcripts, for the "how this was attacked" fold

EvidenceRef is a discriminated union like PublishedCitation: a run output by slug, an input column, a stage id, a term. Every field is a model; no dict[str, Any] anywhere in it. Challenge.backing is a string the orchestrator must copy from the pool or an attacker's evidence, and a test checks every backing appears somewhere in the bundle the job was handed. That is the fabrication guard.

The review is information. It changes nothing on the claim: no qualifier is added, no wording corrected. Grounding is kept as its own list because a span landing on nothing is a finding even when no attacker raised a challenge on it, and because the underlines need the offsets. A rewrite is text and a reason; taking one is submit_claim on the new text, which supersedes the first claim and is attacked on its own.

The page, as agreed

  • Top: this run's outputs, nothing else. The attackers live in a fold at the bottom.
  • The sentence with severity on the underlines; the grounding table; the list sorted by weight; the folds.
  • Approve and Decline, on the claim. No action on a challenge: the review is read, not edited. No author/reader split.
  • Rewrite and re-attack: a textarea, or one of the proposed rewrites, and a POST that submits the new text as a new claim superseding the first (what submit_claim already does for a matching context) and attacks it.
  • Claims in the nav, reachable from every page: "N to review" while any claim is submitted, else the count made. Mock: claims.html.
One rule this crosses. project_shell.html says the nav carries no status marks and is a table of contents. A "2 to review" badge is a status mark. Either the rule bends for this one item, or the count sits on the Overview's next-action line instead and the nav item stays plain. Your call before PR 4.

Arch tests that will fire

  • fan-out ceiling on app.web.routers: #927 already moved a router behind include_admin_routers to stay under it; the list route goes in the same router, not a new one.
  • compiler contract: only services import app.compiler, so the web layer starts an attack through app.services.claim_review.
  • runtime contract: reading a run's branches is allowed from app.services.scope only; the bundle builder calls it rather than app.runtime.
  • record placement: ClaimReview in app/models/records/, the lifecycle functions in the service.
  • added-comment length and banned words (canonical, deriv, sorry, unfortunately): the prompts are long prose and go in *_prompt.py modules like the guide's, which is where the size ratchet expects them.

Cost

Seven turns per attack, six of them with a bundle of a few thousand tokens and one structured answer, on Sonnet. The attack runs once per submitted claim and once per re-attack; nothing runs on page load. If that is too much per claim, the four attackers that read code and columns can share one turn and the orchestrator can take the meaning attacker's job; the shape of the record does not change.

Open

  • Table claims. The record and the page assume a sentence over a cell; a table needs units (columns, rows, the frame) in place of phrases. Deferred on purpose.
  • The nav badge against the no-status-marks rule.
  • Approve is one click with no sign-in, as #973 left it. The record stores no approver.
